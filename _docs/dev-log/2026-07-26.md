### 1. `PipelineStageTimeline` 흐름 애니메이션·유량 표현 — 구현 가능성 검토

바로 구현에 들어가지 않고, 먼저 실현 가능성과 기술적 접근 방식을 검토해 `_docs/PPTX_ALIGNMENT_PLAN.md` Phase C-3에 남겼다.

- **React Flow vs SVG**: `PipelineFlowDiagram`(React Flow 기반)은 `animated: true`로 흐름 애니메이션이 내장돼 있지만, `PipelineStageTimeline`은 노드 5~8개짜리 단순 수평 배열이라 라이브러리 오버헤드가 불필요하다고 판단. 이미 같은 저장소에 있는 `PipelineFlowConnector.tsx`(SVG `<path>` + 화살표 마커) 패턴을 확장하는 쪽으로 결론.
- **유량(volume) 기준**: 기존 `PipelineStage.count`는 실제로는 "개체 수"(예: `kafka.mock.ts`의 Partition 612, Broker 5)이지 "초당 처리량"이 아니어서, 선 굵기 소스로 그대로 쓰면 의미가 어긋난다는 걸 mock 데이터를 실제로 확인해서 짚었다. 별도 `volume?: { value: number; unit: string }` 필드를 신설하고, `kafka.mock.ts`에 이미 있던 throughput 지표(`msg/s`, `MB/s`)를 재사용하는 방향으로 결정.
- **단위 혼용 여부**: 페이지마다 이미 `msg/s`/`MB/s`/`GB/s`/`Rows/s`가 스테이지 성격에 따라 자연스럽게 혼용되고 있어서, 강제로 단일 단위로 통일하지 않고 **같은 타임라인 안에서의 상대적 min-max 스케일**로 선 굵기를 계산하기로 결정.
- **마지막 스테이지 처리**: 커넥터는 항상 source(현재 순회 중인) 스테이지의 `volume` 기준으로 그려지므로, 마지막 스테이지는 애초에 그 뒤에 그릴 커넥터가 없어 별도 분기 없이 자연스럽게 처리됨을 확인.

### 4. `PipelineStageTimeline` 커넥터를 고정폭 SVG → `flex-1` 가변폭 CSS 라인으로 재구현

Phase C에서 구현한 SVG 커넥터(고정 `width=48`)가 노드 개수가 적은 화면(Home의 5개 스테이지 등)에서 전체가 왼쪽으로 뭉쳐 보이는 문제가 있었다. 노드 개수와 무관하게 항상 컨테이너 폭을 꽉 채우도록 커넥터 구조를 다시 짰다.

- SVG `<path>` 대신, 각 커넥터를 `flex-1 min-w-8` div로 만들고 그 안에 그라디언트 배경 라인(base) + `repeating-linear-gradient` 배경을 가진 애니메이션 오버레이(흐름 효과) + 우측 고정 크기(8×8) 화살표 SVG를 절대 위치로 겹쳤다.
- 흐름 애니메이션도 SVG `stroke-dashoffset` keyframe에서 CSS `background-position-x` keyframe(`flow-bg`)으로 교체 — `repeating-linear-gradient`는 컨테이너 폭이 얼마든 자동으로 타일링되므로 가변폭에서도 왜곡 없이 그대로 동작한다.
- 마지막 스테이지가 아닌 스테이지들은 `flex-1`로 늘어나 컨테이너 폭을 균등하게 나눠 채우고, 원(circle) 컬럼만 `shrink-0`으로 고정 크기 유지.

참고 파일: `src/components/layout/PipelineStageTimeline/PipelineStageTimeline.tsx`, `src/index.css`

## 🐛 발생한 문제 & 해결

### 문제 1: SVG 화살표 마커가 선을 통째로 집어삼킴
- **원인**: `<marker>`의 기본 `markerUnits`가 `strokeWidth`라서, 마커 크기가 참조하는 path의 `stroke-width`에 비례해서 커진다. 유량에 따라 `strokeWidth`를 최대 7px까지 스케일링했더니 `markerWidth=5 × strokeWidth=7 ≈ 35px`짜리 거대한 삼각형이 48px짜리 SVG 전체를 뒤덮어버렸다.
- **해결**: `markerUnits="userSpaceOnUse"`로 바꿔 마커 크기를 `stroke-width`와 무관하게 고정.
- **참고**: 이후 커넥터를 CSS 기반으로 재구현하면서(문제 4번째 항목) 이 마커 자체가 고정 크기 SVG로 단순화됨.

### 문제 2: 그라디언트 스트로크가 아예 안 그려짐 (완전 투명)
- **원인**: 커넥터 path가 `M2,12 H42`(완전 수평선)라서 geometry bounding box의 height가 0이 된다. SVG 스펙상 `<linearGradient>`의 기본 단위(`gradientUnits="objectBoundingBox"`)는 참조 대상의 bbox 높이가 0이면 해당 그라디언트를 완전히 무효 처리한다 — 즉 `stroke="none"`과 동일하게 렌더링된다. `stroke`를 그라디언트가 아닌 solid color로 바꾸면 정상 렌더링되는 것으로 원인을 좁혔다.
- **해결**: `gradientUnits="userSpaceOnUse"`로 바꾸고 `x1/y1/x2/y2`를 path와 동일한 절대 좌표(2,12 → 42,12)로 명시.
- **참고**: 화면 스크린샷(다운스케일 + JPEG 압축)만으로는 "얇아서 안 보이는 것"과 "아예 안 그려지는 것"을 구분하기 어려웠다. `getComputedStyle`/`getBoundingClientRect`로 DOM 속성을 직접 조회하고, `stroke`를 강제로 `red`/`10px`로 바꿔보는 식으로 렌더링 파이프라인 자체는 정상임을 먼저 격리한 뒤 원인을 좁혔다.

### 문제 3: 라우트 전환 시 클러스터 선택값이 빈 칸으로 보임
- **원인**: `App.tsx`의 `cluster` state를 `"kafka-prod"`로 초기화해뒀는데, `/spark`로 이동하면 `clusterOptions`가 `["spark-prod"]`뿐이라 `Select`의 `value`(`"kafka-prod"`)가 옵션 목록에 없어 빈 값으로 렌더링됐다. Phase D 회귀 테스트 중 발견.
- **해결**: `clusterOptions?.includes(clusterState) ? clusterState : clusterOptions?.[0]`로 현재 라우트의 옵션에 없으면 첫 번째 옵션으로 폴백하도록 파생값을 계산.

### 문제 4: `PipelineStageTimeline`이 노드 적을 때 왼쪽으로 쏠림
- **원인**: 커넥터를 고정 `width=48`인 SVG로 구현해서, 노드가 5개뿐인 화면(Home)에서는 전체 타임라인 실제 폭이 컨테이너보다 훨씬 좁아 왼쪽에만 뭉쳐 보였다.
- **해결**: SVG를 `flex-1` div + CSS 그라디언트/`repeating-linear-gradient` 배경으로 교체해서, 커넥터가 남는 공간을 자동으로 나눠 채우도록 재구현(위 "완료한 작업 4" 참고).

### 문제 5: `TopologyDiagram` tick 핸들러의 `any` 타입 (7/23부터 이월된 baseline 이슈)
- **원인**: `d3.forceLink()`는 런타임에 `source`/`target`을 문자열 id에서 실제 노드 객체로 바꿔치기하는데, `simLinks`는 `edges.map((e) => ({ ...e }))`로 만들어져 `{ source: string; target: string }` 타입 그대로 남아 있었다. tick 핸들러에서 `d.source.x`(x좌표)에 접근하려면 `source`가 객체여야 하는데 타입은 여전히 `string`이라 타입 에러가 나고, 그걸 `any`로 억지로 우회해뒀던 것.
- **해결**: `SimLink = d3.SimulationLinkDatum<SimNode>`(= `source`/`target`이 `string | number | SimNode` 유니온) 타입을 새로 정의하고 `forceLink<SimNode, SimLink>`로 제네릭을 명시. tick 시점엔 이미 노드 객체로 resolve돼 있다는 d3-force의 계약을 그대로 반영해 `(d.source as SimNode).x`로 좁혀 접근하도록 수정. `any` 없이 타입 에러 4건 모두 해소.
- **참고**: 수정 후 브로커 노드를 실제로 드래그해봐서 연결선이 노드를 따라 움직이는 동작이 깨지지 않았음을 확인.

## 💡 배운 점 / 메모

- 구현에 바로 들어가기 전에 "구현 가능한지 검토해달라"는 요청에는, 결론만 주지 말고 실제 mock 데이터(예: `kafka.mock.ts`의 `count`가 사실 개체 수였다는 것)를 확인해서 근거를 대는 게 나중에 재작업을 줄인다 — 이번에도 `count`를 그대로 유량으로 썼다면 Phase C를 다시 짜야 했을 것.
- SVG로 완전 수평/수직선을 그릴 때는 `gradientUnits="objectBoundingBox"`(기본값) + `<marker markerUnits="strokeWidth">`(기본값) 조합이 둘 다 함정이 될 수 있다 — bbox 한 축이 0이 되는 도형에는 처음부터 `userSpaceOnUse`를 쓰는 습관을 들이는 게 낫다.
- 스크린샷 기반 시각 검증은 뷰포트 다운스케일 + JPEG 압축 때문에 "얇아서 안 보임"과 "렌더링 자체가 안 됨"을 혼동하기 쉽다. 의심되면 `getComputedStyle`/`getBoundingClientRect`로 실제 DOM 값을 먼저 찍어보고, 강제로 눈에 띄는 값(굵은 solid color)으로 바꿔 렌더링 파이프라인 자체를 격리 검증하는 게 빠르다.
- 고정 픽셀 크기의 SVG를 flex 레이아웃 안에 섞으면 "가변 폭에 맞춰 늘어나야 하는 요소"를 표현하기 어렵다 — 순수 라인 형태의 UI는 SVG `viewBox` 스케일링보다 `flex-1` + CSS 그라디언트/`repeating-linear-gradient` 배경 쪽이 왜곡 없이 훨씬 다루기 쉬웠다.
- `_docs/PPTX_ALIGNMENT_PLAN.md`처럼 "검토 → 결론 → 미결정 사항 → 최종 결정"을 단계별로 문서에 누적해두면, 나중에 실제 구현할 때 판단 근거를 다시 찾을 필요 없이 문서만 보고 바로 코드로 옮길 수 있었다.
- 텍스트로 정리된 갭 분석 문서만 믿고 구현하면 디테일을 놓친다 — "그림대로"라는 요청을 받고 나서야 원본 PPTX를 직접 열어봤는데, 연결선이 "굵기 스케일링"이 아니라 "선 개수"로 유량을 표현하고 있었다. 목업이 있는 작업은 텍스트 요약본이 아니라 원본을 먼저 봐야 한다.
- pptx-make 스킬의 헬퍼 스크립트(`thumbnail.py`, `extract-text` 등)가 이 환경엔 설치돼 있지 않았다. 이럴 땐 pptx가 결국 zip 아카이브라는 점을 이용해 `unzip`으로 직접 풀고 `ppt/media/imageN.png`(슬라이드 스크린샷)를 찾은 뒤, Python Pillow로 관심 영역만 크롭·확대해서 보는 우회 경로가 유효했다.
- d3-force처럼 "런타임에 타입이 바뀌는" 라이브러리(문자열 id → 노드 객체 참조로 in-place 치환)를 다룰 때는, 라이브러리가 제공하는 제네릭 타입(`SimulationLinkDatum<T>` 등)을 끝까지 따라가서 정확히 표현하면 `any` 없이도 타입이 맞는다 — 귀찮다고 `any`로 넘기면 나중에 "왜 이렇게 했는지" 다시 조사해야 한다.
