`_docs/images/kpiCard-Total traffic(in,out).png` 목업 이미지가 실제로는 `homeTrend.series`(`src/mocks/home.mock.ts:216`)의 "Traffic In"/"Traffic Out" 두 라인을 하나의 합산 숫자로 요약한 카드라는 걸 확인했다. 현재 `Home.tsx`의 `homeKpis` 그리드(2-2~2-4)에는 아직 구현되어 있지 않고, PPTX 기획 자료에만 존재하는 상태라는 것도 함께 짚었다.

### 2. Traffic 트렌드 차트 y축 분리 (파란 선 안 보임 버그)

"Traffic & Throughput Trend" 섹션(`TrendLineChart`)에서 `Traffic In`(GB/s, 값 3.8~4.3)과 `Events`(eps, 값 1,200~1,340)가 같은 y축을 공유하고 있어서, Events의 스케일에 눌려 Traffic In/Out 두 라인이 축 하단에 거의 평평하게 붙어버리는 것이 원인이었다. 여기에 echarts가 `series` 배열 뒤쪽 항목을 위에 그리는 특성 때문에 Traffic Out(초록)이 Traffic In(파랑) 위를 덮는 문제도 겹쳐 있었다.

`SeriesConfig`(`src/tokens/base.types.ts`)에 `yAxisGroup?: "primary" | "secondary"` optional 필드를 추가하고, `TrendLineChart.tsx`에서 `secondary`로 지정된 시리즈가 하나라도 있으면 y축을 2개(primary/secondary)로 분리해 `yAxisIndex`로 매핑하도록 수정했다. 기존처럼 `yAxisGroup`을 안 쓰는 차트는 단일 축 그대로 동작해 다른 사용처(예: `StackedBarChart`)에는 영향 없다. `home.mock.ts`의 `Events (eps)` 시리즈에 `yAxisGroup: "secondary"`를 지정해 GB/s 두 라인과 eps 라인을 축 단위로 분리했다.

참고 파일: `src/tokens/base.types.ts`, `src/components/charts/TrendLineChart/TrendLineChart.tsx`, `src/mocks/home.mock.ts`

### 3. `yAxisGroup` 리터럴 widening TS 에러 수정

위 수정 직후 `yAxisGroup: "secondary"`가 `SeriesConfig[]`에 할당 불가하다는 타입 에러가 발생했다. 원인은 `homeTrend`가 명시적 타입 주석 없이 객체 리터럴로 export되어 있어서, TS가 문자열 리터럴 `"secondary"`를 좁은 리터럴 타입이 아니라 `string`으로 widening했기 때문이었다(`const` 객체 리터럴의 프로퍼티 값은 contextual typing이 없으면 기본적으로 넓혀짐). `yAxisGroup: "secondary" as const`로 고정해서 해결했다.

참고 파일: `src/mocks/home.mock.ts:232`

### 6. `TopologyDiagram.tsx` 타입 에러 수정

pnpm 전환 후 `pnpm run build`(`tsc -b`)를 처음 돌려보니 `TopologyDiagram.tsx:51`에서 `d3.drag<SVGGElement, SimNode>()`를 `.call()`에 넘기는 부분이 타입 불일치로 실패했다. `@types/d3` 버전(7.4.3)이 npm 때와 동일하다는 걸 `git show HEAD:package-lock.json`으로 확인해서, pnpm 전환이 아니라 원래 있던 잠재 버그(`vite dev`는 타입체크를 안 해서 안 드러났던 것)임을 먼저 확인한 뒤 수정했다. 47번 줄 `.selectAll("g")`에 제네릭 타입 인자가 빠져 있어서 반환 타입이 `Selection<BaseType, ...>`으로 넓혀지고, 그 뒤 `.join("g")`을 거치며 `SVGGElement | BaseType` 유니언이 되어 `d3.drag`가 기대하는 `Selection<SVGGElement, ...>`와 맞지 않았던 것. `.selectAll<SVGGElement, SimNode>("g")`로 제네릭을 명시해 해결했고, `pnpm run build`가 정상적으로 통과하는 것까지 확인했다.

참고 파일: `src/components/topology/TopologyDiagram/TopologyDiagram.tsx:47`

### 7. KpiCard 스파크라인 ↔ TopHeader 기간 선택 연동

echarts `matrix-sparkline` 예제(표 레이아웃 전체가 아니라 그 안의 "호버 시 해당 시점 값이 뜨는" 개별 스파크라인 인터랙션만 이식하고 싶다는 요청)를 참고해서, `SparklineChart`의 데이터 계약을 `number[]`에서 기존 공용 타입 `ChartDataPoint[]`(`src/tokens/base.types.ts`)로 바꿨다. `xAxis`를 `type:'time'`으로 바꾸고, `range`가 주어지면 보이지 않는 `dataZoom(type:'inside')`으로 구간만 제한하도록 했다. `TopHeader`의 `dateRange`/`timeUnit` state는 그동안 아무 데도 연결 안 된 순수 UI 장식이었는데, `App.tsx → Home.tsx → KpiCard → SparklineChart`로 배선하고 `src/lib/resolveTimeRange.ts`(신규)가 "날짜 범위를 명시적으로 골랐으면 그게 우선, 아니면 timeUnit이 결정하는 기본 lookback"을 계산하도록 했다. 기존 5~6개짜리 정적 트렌드 배열로는 "기간 선택 → zoom" 결과가 안 보여서, 시드 고정 랜덤워크로 타임스탬프 붙은 시계열을 생성하는 `src/mocks/trend.ts`(신규, `generateTrendSeries`/`toPoints`)를 추가했다. `SparklineChart`의 데이터 계약이 바뀌면서 이걸 쓰던 다른 곳(`PipelineFlowNode`/`PipelineFlowDiagram`, `PpsMinIO` HPA 테이블, 각 스토리 파일)도 전부 타입에 맞춰 함께 고쳐야 했다.

참고 파일: `src/components/charts/SparklineChart/SparklineChart.tsx`, `src/lib/resolveTimeRange.ts`, `src/mocks/trend.ts`, `src/pages/Home.tsx`, `src/App.tsx`

### 8. 스파크라인 구간을 `Last refresh` 시각에 정확히 앵커링

"timeUnit 5m 선택 시 라인 오른쪽 끝 호버하면 정확히 Last refresh 시각, 왼쪽 끝은 그 5분 전이 찍혀야 한다"는 요구사항에 맞추기 위해, 트렌드 생성의 기준 시각("now")을 `Date.now()`가 아니라 실제 `Last refresh` 값으로 바꿔야 했다. `useAutoRefresh` 훅이 그동안 포맷된 문자열(`toLocaleTimeString()`)만 반환하던 걸 실제 `Date` 객체를 반환하도록 바꾸고, `TopHeader` 표시용 문자열 변환은 호출부(`App.tsx`)로 옮겼다. `generateTrendSeries`/`toPoints`에 `anchor`(기준 시각, epoch ms) 옵션을 추가하고, `Home.tsx`에서 `lastRefresh`를 `useMemo` 키로 삼아 KPI 트렌드를 렌더마다 재생성하게 했다 — 시드는 KPI 값 기반이라 그래프 "모양"은 안정적으로 유지되고 시간축만 lastRefresh를 따라 흘러간다. 또한 `resolveTimeRange`의 `LOOKBACK_MS`가 "5m 토글 = 1시간 조회창"처럼 잘못 매핑돼 있던 걸 "5m 토글 = 실제 5분 조회창"으로 바로잡았다.

참고 파일: `src/hooks/useAutoRefresh.ts`, `src/lib/resolveTimeRange.ts`, `src/mocks/trend.ts`, `src/pages/Home.tsx`

### 9. Home KPI 카드를 PPTX 목업 순서/디자인에 맞춰 재구성

`_docs/images/kpiCard-*.png` 6장(Total Traffic → Total Events/sec → Pipeline Latency → Processing Throughput → Error Rate → Active Alerts)을 참고해서 `homeKpis`를 이 순서·값·색상(정상=초록, 지연=파랑, 처리량=주황, 에러율=빨강)으로 재구성하고, `Home.tsx`의 KPI 그리드를 `grid-cols-3` → `grid-cols-6`으로 바꿨다. `KpiCard.tsx`에는 타입에만 정의돼 있고 실제로는 렌더링되지 않던 `breakdown` 필드를 처음으로 그리도록 추가했다(Active Alerts의 "Critical 1 / Warning 2" 컬러 텍스트 + 우측 상단 종 아이콘). 숫자 값엔 `toLocaleString()`으로 천 단위 콤마를 붙였다. 이 과정에서 `trend.ts`의 변동폭 계산이 `Math.max(|value|, 1)`로 최솟값을 1로 고정해놓은 버그를 발견했다 — Error Rate(0.021)처럼 1보다 훨씬 작은 값은 스파크라인이 계속 0으로 튕기며 들쭉날쭉해졌다.

## 🐛 발생한 문제 & 해결

### 문제 1: Traffic & Throughput Trend 차트에서 Traffic In(파란 선)이 안 보임
- **원인**: `TrendLineChart.tsx`가 시리즈 3개(Traffic In, Traffic Out, Events)를 단일 y축에 그렸는데, Events(eps, 1,200~1,340)의 스케일이 Traffic In/Out(GB/s, 3~4)보다 300배 이상 커서 축이 0~1,400 범위로 잡히고 GB/s 라인 두 개가 축 하단에 거의 평평하게 눌림. 게다가 `series` 배열 순서상 Traffic Out이 Traffic In 뒤에 그려져 겹치는 구간에서 위를 덮어버림.
- **해결**: `SeriesConfig.yAxisGroup`을 추가하고 `TrendLineChart`에서 `secondary` 시리즈를 별도 y축(`yAxisIndex: 1`)에 매핑. `Events (eps)`만 secondary로 지정.
- **참고**: `hasSecondaryAxis`가 false일 때는 기존과 동일하게 단일 축으로 동작하므로 다른 `TrendLineChart` 사용처에는 영향 없음.

### 문제 2: `yAxisGroup: "secondary"` 할당 시 TS2322 에러
- **원인**: `homeTrend`가 타입 주석 없는 객체 리터럴이라 TS가 문자열 리터럴 프로퍼티를 `string`으로 widening. `SeriesConfig.yAxisGroup`은 `"primary" | "secondary"` 유니언이라 넓혀진 `string`과 불일치.
- **해결**: `"secondary" as const`로 리터럴 타입 고정.
- **참고**: `as const` 없이 타입을 좁히려면 `homeTrend: { series: SeriesConfig[]; ... }` 같은 명시적 타입 주석을 붙이는 방법도 있지만, 필드 하나만 문제였으므로 최소 변경으로 `as const`를 택함.

### 문제 3: `pnpm run build` 시 `TopologyDiagram.tsx`에서 TS2345 에러 발생
- **원인**: `.selectAll("g")`에 제네릭 타입 인자가 없어서 반환 타입이 `Selection<BaseType, ...>`으로 넓혀졌고, `.join("g")` 이후 `SVGGElement | BaseType` 유니언이 되어 `d3.drag<SVGGElement, SimNode>()`가 기대하는 `Selection<SVGGElement, ...>`와 구조적으로 맞지 않음. npm 사용 시에도 존재했던 버그지만 `vite dev`는 타입체크를 생략해서 드러나지 않았음.
- **해결**: `.selectAll<SVGGElement, SimNode>("g")`로 제네릭 명시.
- **참고**: pnpm 전환이 원인인지 먼저 의심했으나, `git show HEAD:package-lock.json`으로 `@types/d3` 버전(7.4.3)이 npm 때와 동일함을 확인해 무관함을 확인 후 수정.

### 문제 4: 스파크라인 호버 시 카드 밖으로 툴팁이 잘림
- **원인**: `Card`(`src/components/ui/card.tsx`)와 `StatusDataTable` 셀이 둘 다 `overflow-hidden`이라, echarts 툴팁이 기본값(차트 컨테이너 내부에 append)으로 렌더되면 카드 경계에서 잘림.
- **해결**: `tooltip.appendToBody: true`로 툴팁을 `document.body`에 붙여서 컨테이너의 `overflow-hidden`을 우회.
- **참고**: `SparklineChart`처럼 아주 작은 컨테이너(24~40px)에 들어가는 차트는 기본적으로 이 옵션을 켜두는 게 안전.

### 문제 5: Error Rate(0.021%) 카드의 스파크라인이 0으로 계속 튕기며 들쭉날쭉함
- **원인**: `generateTrendSeries`의 변동폭 계산이 `(rand()-0.5)*2*volatility*Math.max(Math.abs(endValue), 1)`이라, endValue가 1보다 작으면 무조건 스케일 기준을 1로 고정해버려서 값(0.021) 대비 변동폭이 수백~수천 배로 부풀려짐. `Math.max(0, prev+delta)`로 음수를 0으로 클램프하는 로직과 겹쳐 계속 0에 부딪히며 스파이크치는 모양이 됨.
- **해결**: `Math.max(Math.abs(endValue), 1)` → `Math.abs(endValue) || 1`(0일 때만 1로 폴백)로 수정. 반올림도 `Math.round(v*100)/100` → `Math.round(v*10000)/10000`으로 정밀도를 올려 0.02 근처 값들이 뭉개지지 않게 함.
- **참고**: 6개 KPI 카드 중 값이 1보다 작은 건 Error Rate뿐이라 지금까지 드러나지 않았던 잠재 버그.

## 💡 배운 점 / 메모

- 한 차트에 단위가 다른 지표(GB/s vs eps)를 같이 그릴 땐 처음부터 듀얼 y축을 염두에 둬야 한다 — 값 차이가 수백 배 나면 작은 쪽 시리즈는 사실상 안 보이는 게 당연한 결과다.
- echarts는 `series` 배열의 뒤쪽 항목을 위에 그리므로, 스케일이 눌려 겹치는 라인이 있을 땐 순서도 시각적 결과에 영향을 준다는 걸 기억해둘 것.
- `const` 객체 리터럴의 문자열 프로퍼티는 기본적으로 widening되므로, 유니언 리터럴 타입을 쓰는 optional 필드를 mock 데이터에 추가할 땐 `as const`를 잊지 않아야 한다.
- 패키지 매니저 전환 여부는 workspaces/`.npmrc`/CI/postinstall 스크립트 유무로 빠르게 판단할 수 있다 — 단일 패키지 프로젝트면 lockfile 교체 + 설치 한 번으로 끝나는 경우가 많다.
- `vite dev`(esbuild 변환)는 타입체크를 하지 않으므로, 평소 dev 서버만 돌리다 보면 `tsc -b`에서만 드러나는 타입 에러가 오래 방치될 수 있다. 정기적으로 `build`를 돌려보는 습관이 필요.
- pnpm은 기본적으로 의존성의 postinstall 빌드 스크립트를 차단한다(`ERR_PNPM_IGNORED_BUILDS`) — `esbuild` 같은 네이티브 바이너리를 설치하는 패키지는 `pnpm approve-builds`로 명시 승인해야 정상 동작한다.
- 목업(mock) 시계열의 "현재 시각" 앵커는 실제 데이터가 아니라 데모용으로 임의 생성한 것이라도, 화면에 실제로 보여지는 "지금" 개념(여기선 `Last refresh`)과 반드시 일치시켜야 한다 — `Date.now()`로 따로 앵커링하면 표시되는 시각과 실제 데이터 시각이 미묘하게 어긋난다.
- 작은 값(1 미만)에 적용되는 랜덤워크/노이즈 생성 로직은 "최소 변동폭"을 상수로 고정하면 상대적으로 값이 작을수록 왜곡이 커진다 — 변동폭은 항상 기준값 자체에 비례시키고, 0 근처에서만 별도 폴백을 두는 게 안전.
- 컴포넌트 타입에 필드는 정의돼 있는데 실제 렌더링 로직이 없는 경우(`breakdown`)가 있을 수 있으니, mock 데이터를 참고해서 "이 필드가 왜 안 보이지?"를 확인할 때는 타입 정의 여부가 아니라 실제 렌더 코드를 봐야 한다.
